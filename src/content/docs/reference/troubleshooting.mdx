When something does not work, the panel usually tells you why: a website in the **Problem**
state shows the server's error message, and every background task shows its result under
**Recent tasks**. This page covers the problems people run into most, and where to look when
the panel cannot tell you.

<Aside type="tip">
Run the commands on this page on the server, over SSH, as a user who can use `sudo`.
</Aside>

## Where the logs are

Every ekPanel part and every service it sets up runs under systemd, so `journalctl` shows its
log. Add `-f` to follow new lines, or `--since "10 min ago"` to see a short time span.

```bash
sudo journalctl -u ekpanel -u ekpanel-agent --since "10 min ago"
```

| Unit | What it is | When it exists |
| --- | --- | --- |
| `ekpanel` | The panel | On the panel's server |
| `ekpanel-agent` | The agent | On every server (made by the installer) |
| `ekpanel-agent-rollback` | A timer that puts the previous agent back if an update fails | Only during an agent update |
| `caddy` | Web server for the panel, websites and apps | On every server set up by the installer |
| `postgresql` | The panel's database, and customers' PostgreSQL databases | Panel's server; servers with PostgreSQL databases |
| `mariadb` | MariaDB databases | After the first MariaDB database |
| `php8.4-fpm` (any version) | PHP of administrators' websites | After the first PHP website with that version |
| `ekpanel-php8.4-c<customer>` | PHP of one customer's websites, inside their limits | Customers with PHP websites |
| `ekpanel-cron-<job id>` | One cron job's runs and output | For each cron job |
| `ekpanel-mail` | The mail server (Stalwart) | Email turned on |
| `pdns` | PowerDNS name server | The server is a name server |
| `crowdsec`, `crowdsec-firewall-bouncer` | CrowdSec and its firewall bouncer | CrowdSec turned on |
| `clamav-freshclam` | ClamAV's virus database updates | Malware scans turned on |
| `pure-ftpd` | FTP server | Any website has FTP on |
| `docker` | Docker | After the first Docker app |
| `ekpanel-countries` | Loads country blocking rules at boot | Country blocking on |

Other logs are files:

| File | What it shows |
| --- | --- |
| `/var/log/caddy/site-<site id>.log` | Requests to one website (also in the panel, on the website's page) |
| `/var/log/caddy/app-<app id>.log` | Requests to one app |
| `/home/<account>/logs/php-error.log` | A website's PHP errors (also in the panel) |

## I cannot reach the panel

The panel itself listens only on `127.0.0.1:8080`. Caddy answers on ports 80 and 443 and passes
requests on. So check both, from the server:

<Steps>

1. Is the panel running?

   ```bash
   curl -fsS http://127.0.0.1:8080/api/v1/health
   ```

   You should see `{"status":"ok",...}`. If not, read `journalctl -u ekpanel -n 100`. A common
   cause is that PostgreSQL is not running: `sudo systemctl status postgresql`.

2. Is Caddy running, and is its configuration valid?

   ```bash
   sudo systemctl status caddy
   sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
   ```

3. Do ports 80 and 443 reach the server? Many providers have a **cloud firewall** in their web
   console that blocks everything you did not open. Open TCP 80 and 443 there (and 7443 for
   other servers' agents). If you use `ufw` yourself, allow them too.

4. With `--domain`: does the name point at this server? `dig +short panel.example.com` must
   show the server's address. Caddy can only get a certificate after it does.

</Steps>

## The browser warns about the certificate

If you installed without `--domain`, the panel uses a **self-signed certificate** for the
server's IP address. Browsers warn about it once, because nobody they trust signed it. The
connection is still encrypted. You can accept the warning, or switch to a trusted certificate:

<Steps>

1. Point a DNS name, such as `panel.example.com`, at the server's address.
2. Run the installer again with that name, the same way you installed:

   ```bash
   curl -fsSL https://github.com/ekPanel/ekpanel/releases/latest/download/install.sh | sudo bash -s -- --domain panel.example.com
   ```

   or, from your own build, `sudo ./install.sh --local-dir . --domain panel.example.com`.

3. Open `https://panel.example.com`. Caddy gets a free Let's Encrypt certificate on the first
   visit; this needs port 80 and 443 open to the internet.

</Steps>

## I lost the setup token

Until the first administrator exists, the token is kept in a file and in the panel's log:

```bash
sudo cat /var/lib/ekpanel/setup-token
sudo journalctl -u ekpanel | grep setup_token
```

The token is deleted as soon as the first administrator is created.

## "Too many attempts"

After 10 failed sign-ins from one address, or for one email address, the panel refuses
sign-ins for 15 minutes. Wait, then try again. If you use two-factor authentication, check
that your phone's clock is right: codes change every 30 seconds.

## I lost the phone with my two-factor codes

From the next release, use one of your recovery codes in the code field of the sign-in page, or
sign in with a passkey if you added one. An administrator can reset a customer's two-factor
sign-in on the customers list. For an administrator's account, run this on the panel's server:

```bash
sudo -u ekpanel ekpanel reset-2fa admin@example.com
```

Then sign in with the password and turn two-factor sign-in on again. See
[If you lose your phone](/guides/security/accounts/#if-you-lose-your-phone).

## A server shows as offline

The panel marks a server offline when its agent's connection is gone, and sends a
notification after 3 minutes.

<Steps>

1. Is the server itself up? Can you reach it with SSH?

2. Is the agent running?

   ```bash
   sudo systemctl status ekpanel-agent
   sudo journalctl -u ekpanel-agent -n 100
   ```

   The installer makes the `ekpanel-agent` service on every server it sets up. If you started
   an agent by hand with `sudo ekpanel-agent run`, check that it still runs.

3. Can the server reach the panel on TCP 7443? From the managed server:

   ```bash
   nc -vz panel.example.com 7443
   ```

   If not, open TCP 7443 on the **panel's** server (cloud firewall and `ufw`).

4. Does the agent's log repeat "lost connection to panel; retrying" with a certificate error,
   or say that `/etc/ekpanel/agent.json` is incomplete? Then the server must be connected
   again (for example after its certificate was revoked). Click **New connection command** on the server's
   page in the panel and run `sudo ekpanel-agent enroll` on the server with the `--panel`,
   `--token` and `--ca-pin` values of the new command, then
   `sudo systemctl restart ekpanel-agent`. (The one-line install command does not enrol a server
   that already has a credential.)

</Steps>

Changes you make while a server is offline wait: the panel shows "is offline. The settings are
applied as soon as its agent reconnects." Nothing is lost.

## A new server stays "Not connected yet"

The token in the connection command works **once** and expires **after one hour**. If it
expired or was used, click **New connection command** and run the new command. If `enroll`
fails with a pin or certificate error, check that you copied the whole command, including the
`--ca-pin` value. If it cannot connect at all, check port 7443 as above.

## A website shows "Problem"

The page shows **The server could not apply this website's settings** and the server's error
message. Read the message first: it usually names the cause (for example, a PHP version that
did not start).

<Steps>

1. Fix the cause if the message names one. For PHP pools, the PHP log helps:

   ```bash
   sudo journalctl -u php8.4-fpm -n 100
   ```

2. Click **Try again** on the website's page. It sends the website's settings to the server
   again.

3. If it still fails, read `journalctl -u ekpanel-agent` around that time.

</Steps>

The panel also applies every server's whole state again every 10 minutes and whenever an agent
reconnects, so a passing problem (a slow package download, for example) often fixes itself.
A Caddy configuration the web server rejects is rolled back and reported on that website
only, so other websites keep working.

## A website has no valid certificate

Caddy gets free certificates from Let's Encrypt by itself. It needs the domain's DNS records
to point at the server, and ports 80 and 443 open. If you use Cloudflare's proxy, set the
zone's SSL mode to **Full (strict)** (the DNS page has a switch for it). Caddy's log says
what went wrong:

```bash
sudo journalctl -u caddy --since "30 min ago" | grep -i -E "error|challenge"
```

## A website shows "Website suspended" or "Bandwidth used up"

From the next release, these short pages (with HTTP status 503) come from ekPanel itself, not
from the website:

- **"Website suspended"**: an administrator has
  [suspended](/guides/admin/customers/#suspend-a-customer) the website's owner. The customers
  list shows "Suspended since …". Click **Unsuspend** to bring everything back.
- **"Bandwidth used up"**: the owner's package stops websites once its monthly
  [bandwidth](/guides/admin/customers/#how-bandwidth-is-counted) is used up. The customers list
  shows "Bandwidth used up: websites stopped". It ends by itself in the next month (UTC), or at
  once with a larger package.

The same pages show on the addresses of the customer's apps.

## The name server will not start (port 53)

PowerDNS listens on port 53 of the server's own addresses (loopback and the network cards'
addresses, not Docker's bridges). The system's resolver, `systemd-resolved`, keeps
`127.0.0.53`, so the two do not collide.

If another DNS server already listens on port 53 of those addresses (for example `bind9` or
`dnsmasq`), PowerDNS cannot start. Find it:

```bash
sudo ss -lunpt 'sport = :53'
```

Stop and disable the other DNS server if you do not need it, then save the name server
settings in the panel again. `journalctl -u pdns` shows PowerDNS's own error.

## Malware scans fail on small servers

ClamAV needs a lot of memory while it scans: the panel warns on servers with less than 2 GB,
and estimates about 1.5 GB during a scan. On a smaller server, scans may be stopped by the
kernel. Add memory or swap, or keep scans off.

Right after you turn scans on, ClamAV first downloads its virus database (about 250 MB). Until
it is done, a scan answers "ClamAV is still downloading its virus database". Wait a few
minutes. A full scan of many files runs at the lowest priority and can take more than an hour.

## Automatic updates and restarts

On a fresh server, the system often installs updates by itself in its first minutes. When the
agent installs a package (PHP, MariaDB, Docker…) during that time, it waits up to 5 minutes for
the package manager. A task that still fails can simply be started again.

If you turn on automatic security updates (on the **Server security** page), updated services
restart after an update. That is normal. Note:

- If the agent restarts, open web terminals and running Git builds end, because they belong to
  the agent's connection. Open or start them again.
- After every reconnect the panel applies the server's state again, so websites and apps come
  back as they should be.
- The checklist on the **Server security** page shows when the server needs a restart.

## A task failed

Open **Recent tasks** (the task tray) to see the error. Most tasks can simply be started
again. Tasks that were running when the panel stopped are picked up again when it starts.
For details, see `journalctl -u ekpanel` and, for work on a server, `journalctl -u ekpanel-agent`.

## Updates

- **"Update to … failed" and the previous version was kept.** The panel's new version did not
  start, or did not report its version within 90 seconds, so the agent put the old program
  back. The new one is in `/usr/local/bin/ekpanel.failed`. Read why it failed with
  `sudo journalctl -u ekpanel --since "30 min ago"`; a failed database change is reported
  there. If the update stopped before that (a download, signature or trial-run error), nothing
  was changed. See [When an update fails](/start/upgrade/#when-an-update-fails).
- **A server shows Failed in the update's results.** Its new agent did not reach the panel
  within the panel's wait, and its rollback timer puts the previous agent back within 3
  minutes (the new one is kept as `ekpanel-agent.failed`). On that server, read
  `sudo journalctl -u ekpanel-agent` and `sudo systemctl status ekpanel-agent`. When the cause
  is fixed, click **Update 1 agent** on the **Updates** page.
- **"The agent on the panel's own server is not connected, so it cannot install the
  update."** That agent installs new panels. On the panel's server, check
  `sudo systemctl status ekpanel-agent`. If the agent was never enrolled there (for example a
  panel started without the installer), run the installer once.
- **"The last check failed: …" on the Updates page**: the panel cannot reach `github.com` (or
  the mirror in `EKPANEL_RELEASES_URL`). Check the server's outgoing HTTPS and DNS.
- **The installer refuses a download** with "SHA256SUMS is not signed by the ekPanel release
  key; not installing." or "… does not match its signed checksum; not installing.": the file
  was changed or cut off on the way, and nothing was installed. Try again later or from
  another network. A `--release-url` mirror must serve the official files unchanged.

## Run the installer again

Running `install.sh` again is safe. It upgrades the programs to the version it downloads (or
the one in `--local-dir`) and keeps your data:

```bash
curl -fsSL https://github.com/ekPanel/ekpanel/releases/latest/download/install.sh | sudo bash -s -- [--domain panel.example.com]
sudo ./install.sh --local-dir . [--domain panel.example.com]
```

It installs the new programs (keeping the old ones as `.prev`), writes the settings files and service files again, restarts the
panel and the agent, and writes the Caddyfile again. It connects the agent again only if
`/etc/ekpanel/agent.json` has no credential. Changes you made by hand to `panel.env`, the
service files or the Caddyfile are lost. See [Configuration](/reference/configuration/).
