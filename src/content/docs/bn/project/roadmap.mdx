ekPanel ধাপে ধাপে (phase) বানানো হচ্ছে। প্রতিটা phase শেষ হয় এমন কিছু দিয়ে যা আপনি একটা আসল server-এ
install করে ব্যবহার করতে পারেন। **Phase 0 থেকে 3 শেষ হয়েছে**, phase 4-এর প্রথম অংশটাও: release আর
update (4a)। এখান থেকেই 9 November 2026-এ প্রথম release, v0.1.0, বের হয়েছে। এরপর 4b-এর API অংশ (API token, OpenAPI
description আর `ekctl` command-line tool) শেষ হয়েছে, আর আসবে পরের release-এ, 4c-ও তাই: একটা website, app, database বা একজন customer-এর এক server-এর সবকিছু অন্য
server-এ সরানো, আর server চলে গেলে একটা website তার backup থেকে অন্য server-এ আবার বানানো। 4d, importer-ও শেষ: একটা পুরো cPanel account তার full backup থেকে
import করা যায়, তার website, file, MySQL database, mail-সহ email, cron job আর DNS zone নিয়ে; aaPanel বা অন্য যেকোনো
host থেকে একটা একটা করে website, তার file-এর archive আর database dump থেকে; আর Coolify-এর application আর service, তার API
দিয়ে। 4e শুরু হয়েছে: এর প্রথম অংশ, account-এর নিরাপত্তা (two-factor sign-in-এর recovery code, কারও
two-factor sign-in reset করা, sign in থাকা device-এর তালিকা, আর passkey), শেষ হয়েছে আর আসবে পরের release-এ, এর
দ্বিতীয় অংশটাও তাই: customer suspend করা, website আর অন্য জিনিসের মালিক বদলানো, package-এ bandwidth limit, আর ব্যর্থ
cron job-এর alert, এর তৃতীয় অংশ: reseller, আর চতুর্থ অংশ: white-label branding। এরপর sub-user।
প্রতিটা সিদ্ধান্ত আর test-সহ পুরো plan আছে main repository-র
[`PLAN.md`](https://github.com/ekPanel/ekpanel/blob/HEAD/PLAN.md)-এ।

<Aside type="caution" title="এখনো শুরুর দিকের software">
নিচে "শেষ" মানে একটা test server-এ (একটা local VM) বানানো আর test করা, production-এ ব্যবহার করা নয়।
প্রথম release, v0.1.0, বের হয়েছে: চালিয়ে দেখুন, test করুন, কিন্তু এখনই এতে গুরুত্বপূর্ণ কিছু host
করবেন না।

## শেষ হয়েছে

### Phase 0: ভিত্তি <Badge text="শেষ" variant="success" />

যে ভিত্তির ওপর বাকি সবকিছু বসে: panel আর agent, mutual TLS দিয়ে যুক্ত (agent বাইরের দিকে connect করে,
তাই NAT-এর পেছনের server কাজ করে); setup token দিয়ে sign in, argon2id password, two-factor
authentication আর rate limit; role; একটা append-only audit log; PostgreSQL-এ একটা task queue; ৩০ দিনের
history-সহ live server statistics; English আর বাংলায় web UI, ডান-থেকে-বাম ভাষার জন্য তৈরি; আর test VM
script-সহ `install.sh`।

## এরপর: phase 4, "আরও এগিয়ে"

৯ নভেম্বর ২০২৬ তারিখে ঠিক করা হয়েছে। অংশগুলো এই ক্রমে আসবে, প্রতিটা phase 3-এর মতো VM-এ test করা হবে।
Billing আসবে সবার শেষে, কারণ এটা API token (4b) আর reseller-এর (4e) ওপর নির্ভর করে।

### 4a. Release আর update <Badge text="শেষ" variant="success" />

VM-এ test key দিয়ে sign করা test release দিয়ে বানানো আর পরীক্ষা করা হয়েছে। **এখান থেকেই 9 November
2026-এ প্রথম release, [v0.1.0](https://github.com/ekPanel/ekpanel/releases/tag/v0.1.0), publish হয়েছে।**
এরপর আসছে 4b।

- CI-তে release build (Linux amd64 আর arm64), একটা tag থেকে হুবহু আবার বানানো যায় (reproducible),
  sign করা checksum তালিকা আর GitHub build attestation-সহ
- [এক লাইনের একটা installer](/start/install/), যা একটা release download করে আর এর signature check
  করে; `--agent` দিলে এটা agent আর web server-সহ [দ্বিতীয় একটা server set up করে](/start/add-server/)
- [Self-update](/start/upgrade/): panel নতুন release দেখায়, নিজেকে update করে (পুরোনো program রেখে
  দিয়ে, আর নতুনটা চালু না হলে সেটা ফিরিয়ে এনে), তারপর প্রতিটা agent update করে, একবারে একটা server
- Changelog থেকে release notes, আর [আপডেট](/guides/admin/updates/) page-এ প্রতিটা server-এর agent
  version
- এখনো বাকি: একটা web translation platform (Weblate বা এমন কিছু)

Release কীভাবে বানানো হয়: একজন owner `pub`-এ `vX.Y.Z` tag দেন। Release workflow amd64 আর arm64-এর জন্য
reproducible archive build করে, সুরক্ষিত `release` environment-এ রাখা key দিয়ে `SHA256SUMS` sign করে,
build attestation যোগ করে, আর release publish করে। `v1.2.3-rc.1`-এর মতো tag pre-release হয়, যা panel
কখনো update হিসেবে দেখায় না।

### 4b. API, CLI, Terraform <Badge text="আংশিক শেষ" variant="caution" />

`dev` branch-এ শেষ আর test করা হয়েছে; আসবে **পরের release-এ** (v0.1.0-এ নেই):

- প্রতি user-এর [API token](/guides/security/api-tokens/), scope আর মেয়াদ-সহ, একবার দেখানো, revoke করা যায়, আর
  audit log-এ এর নাম থাকে। Customer-দেরও আছে, কম scope নিয়ে। Token কখনো account-এর নিরাপত্তা বদলাতে, token
  manage করতে বা terminal খুলতে পারে না
- পুরো API-এর একটা [OpenAPI description](/reference/api/#the-openapi-description), `/api/v1/openapi.json`-এ (আর
  `docs/openapi.json`-এ), router থেকে বানানো আর CI-তে check করা, প্রতিটা operation-এর দরকারি scope-সহ; আর এই API
  docs
- [`ekctl`](/reference/cli/), Linux, macOS আর Windows-এর জন্য একটা command-line tool: server, website, database,
  app, DNS, backup আর task, `--json` output, আর যেকোনো endpoint-এর জন্য `ekctl api`
- একটা background task-এর খোঁজ রাখতে `GET /api/v1/tasks/{id}`

এখনো বাকি:

- একটা Terraform provider, phase 4-এর পরের দিকে, API stable হলে। OpenAPI description-এ request আর response schema
  আসবে এর সাথে
- ধীর কাজের খোঁজ রাখার একটাই উপায়: কাজ শুরু করে এমন প্রতিটা উত্তরে একটা `task_id` (আজ কোনো উত্তর task, কোনোটা
  state-সহ জিনিস, কোনোটা deployment)

### 4c. Server-এর মধ্যে সরানো <Badge text="শেষ" variant="success" />

`dev` branch-এ শেষ; আসবে **পরের release-এ**। Website আর app সরানো, আর backup থেকে আবার বানানো দুটো VM দিয়ে test করা
হয়েছে; database আর customer সরানো এখন পর্যন্ত শুধু panel-এর automated test দিয়ে:

- আপনার বেছে নেওয়া database সহ একটা [website অন্য ekPanel server-এ সরানো](/guides/websites/move/): owner আর ACL-সহ
  file, database, certificate, settings আর cron job। কিছু বদলানোর আগে নতুন server যাচাই করা হয়, panel যে DNS চালায় তা
  পেছনে যায়, আর আপনি না মোছা পর্যন্ত পুরোনো কপি চলতে থাকে। সরানো ব্যর্থ হলে website যেখানে ছিল সেখানেই থাকে
- একটা [app অন্য ekPanel server-এ সরানো](/guides/apps/move/): সংখ্যায় owner-সহ তার Docker volume, Git app-এর বর্তমান
  build (নতুন করে কিছু build হয় না), certificate, settings আর cron job। সরানোর সময় app বন্ধ থাকে; আপনি না মোছা পর্যন্ত
  পুরোনো কপি তার data সহ বন্ধ থাকে, আর সরানো ব্যর্থ হলে app যেখানে ছিল সেখানে আবার চালু হয়। Pull request preview-ওয়ালা
  app সরে না
- আলাদাভাবে একটা [database সরানো](/guides/data/move-database/): dump, switch, তারপর একই user আর password দিয়ে নতুন server-এ
  load; আপনি না মোছা পর্যন্ত পুরোনো কপি থাকে। পুরোনো server-এর website আর app পুরোনো কপিই ব্যবহার করতে থাকে, তাই সাধারণত
  website টাই তার database সহ সরান
- একজন [customer সরানো](/guides/admin/move-customer/): তাঁর এক server-এর সবকিছু, একবারে একটা করে (প্রথম website তাঁর সব
  database সাথে নেয়), প্রথম সরানো শুরুর আগে সব check করা, প্রথম ব্যর্থতায় থেমে যায়; যা সরেছে তা সরানোই থাকে
- Server চলে গেলে আপনার বেছে নেওয়া database সহ একটা [website backup থেকে অন্য server-এ আবার বানানো](/guides/websites/rebuild/):
  recovery key দিয়ে নতুন server-এ S3 storage connect করা হয়, আর website-এর home folder আর database তাদের সবচেয়ে নতুন
  backup থেকে ফেরত আসে। শুধু S3 storage-এর জন্য, কারণ local backup location হারানো server-এই থাকে। দুটো VM আর একটা S3
  test server দিয়ে চালিয়ে দেখা: একই file, owner, ACL আর data সহ প্রায় ১০ second-এ আবার বানানো
- Copy যায় panel-এর সাথে agent-দের নিজস্ব connection দিয়ে, public SSH দিয়ে নয়

পরের জন্য রাখা:

- সরানোর আগে নতুন server-এর খালি disk জায়গা check করা, আর মালিকের সব database-এর বদলে website আসলে যেগুলো ব্যবহার করে
  সেগুলো দেখানো
- App সরানোয়: সরানোর পরে app-এর পাতা খুলে দেখা, আর Git app-এর রাখা build-গুলোও সাথে নেওয়া (ততদিন rollback-এর আগে আবার
  deploy করুন)

### 4d. Importer <Badge text="শেষ" variant="success" />

`dev` branch-এ শেষ; আসবে **পরের release-এ**। প্রতিটা importer VM-এ চালিয়ে দেখা হয়েছে (cPanel আর website archive ইমপোর্ট ওই
host-গুলোর মতো করে বানানো backup দিয়ে, Coolify ইমপোর্ট একটা আসল Coolify v4 দিয়ে)। এরপর 4e।

- cPanel backup: website, file, MySQL database, mail-সহ email, cron job আর DNS zone <Badge text="শেষ" variant="success" />।
  Certificate ইচ্ছা করেই import হয় না: domain server-এ point করলে নতুন certificate নেওয়া হয়
- aaPanel-এর site আর database; অন্য host থেকে সাধারণ WordPress (বা যেকোনো website), website archive import দিয়ে
  <Badge text="শেষ" variant="success" />
- [Coolify-এর application আর service](/guides/admin/import-coolify/), Coolify-এর API দিয়ে
  <Badge text="শেষ" variant="success" />: variable, প্রথম domain আর port, আর রাখা folder-সহ image, Git আর Compose app। Volume-এর
  data admin নিজে কপি করেন; database ইমপোর্ট হয় না
- কী import হয়েছে আর কী হয়নি, তার একটা report <Badge text="শেষ" variant="success" /> (Coolify-এর জন্য প্রতিটা app-এর note)

### 4e. Reseller আর white-label <Badge text="আংশিক শেষ" variant="caution" />

`dev` branch-এ শেষ; আসবে **পরের release-এ**:

- [Account-এর নিরাপত্তা](/guides/security/accounts/) <Badge text="শেষ" variant="success" />:
  - Two-factor sign-in চালু করলে দশটা এক-বারের recovery code, একবারই দেখানো আর শুধু hash হিসেবে রাখা;
    sign-in-এর code-এর field-এ ব্যবহার করা যায়, একটা ব্যবহার হলে alert আর audit log-এ লেখা, আর নিরাপত্তা
    পাতায় নতুন code
  - কারও two-factor sign-in reset করা: customer-এরটা customer তালিকা থেকে, যে কারও panel-এর server-এ
    `ekpanel reset-2fa` দিয়ে। API token দিয়ে কখনো করা যায় না
  - Passkey, আর নিরাপত্তা পাতায় active session-এর তালিকা, যেখান থেকে একটা একটা করে শেষ করা যায়
  - Recovery code আর session একটা local panel-এ browser দিয়ে চালিয়ে দেখা হয়েছে; passkey এখন পর্যন্ত শুধু
    automated test-এ, একটা virtual authenticator দিয়ে, আসল device দিয়ে এখনো নয়
- [Customer](/guides/admin/customers/) <Badge text="শেষ" variant="success" />:
  - [একজন customer-কে suspend করা](/guides/admin/customers/#suspend-a-customer), এমন একটা কারণ-সহ যা শুধু admin-রা
    দেখেন: sign in বন্ধ (password, passkey বা API token), তাঁর website আর app-এর address-এ একটা "suspended" page
    (503), app থামানো, cron job বিরতিতে, SFTP আর FTP বন্ধ, mailbox-এ sign in বন্ধ কিন্তু mail আসতে থাকে। কিছুই মোছা
    হয় না, আর suspend তুলে দিলে সব আগের মতো হয়
  - Website, database, app, email domain আর DNS zone-এর [মালিক বদলানো](/guides/admin/customers/#change-the-owner),
    অন্য customer বা admin-দের কাছে, আগে নতুন মালিকের package মিলিয়ে। Server-এ কিছুই সরে না
  - Package-এ calendar মাস ধরে [bandwidth limit](/guides/admin/customers/#how-bandwidth-is-counted), 90% আর 100%-এ
    alert-সহ, আর package বললে পরের মাস বা বড় package পর্যন্ত website-এ একটা "bandwidth used up" page (503)
  - [ব্যর্থ cron job-এর alert](/guides/websites/cron/#failure-alerts), প্রতি 5 মিনিটে check, আবার একটা run সফল না
    হওয়া পর্যন্ত একবারই
  - Suspend, bandwidth-এ বন্ধ করা, cron alert আর মালিক বদলানো VM-এ চালিয়ে দেখা হয়েছে
- [Reseller](/guides/admin/resellers/) (4e-3) <Badge text="শেষ" variant="success" />:
  - নিজস্ব package আর customer-সহ reseller, administrator-এর দেওয়া সীমার মধ্যে: সব customer মিলিয়ে মোট (customer-দের
    যা আছে তা গুনে, তাই একজন reseller নিজের যা আছে তার বেশি বিক্রি করতে পারেন), একটা package সর্বোচ্চ কতটা দিতে পারে,
    আর তাঁর package কোন PHP version, image, server আর feature দিতে পারবে
  - একজন reseller শুধু তাঁর customer আর তাঁদের জিনিস দেখেন আর সামলান; server, backup, security, import, update বা
    audit log নয়
  - একজন reseller-কে suspend করলে তাঁর সব customer suspend হন; admin-এর করা suspend reseller তুলতে পারেন না
  - সব customer মিলিয়ে একটা bandwidth মোট, alert আর চাইলে বন্ধ করা-সহ; reseller-রা তাঁদের customer-দের alert-ও পান
  - Admin-রা reseller ধরে customer দেখেন, একজন customer-কে অন্য reseller-এর কাছে সরান, আর reseller হিসেবে ঢোকেন
  - VM-এ চালিয়ে দেখা হয়েছে: website-এর মোট, suspend করা আর তোলা, bandwidth-এ বন্ধ করা, reseller-এর customer-দের মধ্যে
    মালিক বদল, আর reseller মোছা
- [Branding (white-label)](/guides/admin/branding/) (4e-4) <Badge text="শেষ" variant="success" />:
  - Admin-দের সেট করা panel-এর নিজের নাম, রং, logo আর domain, আর admin অনুমতি দিলে একজন reseller-এর নিজেরটা, তাঁর আর
    তাঁর customer-দের জন্য
  - Header, browser tab, notification আর authenticator app-এ নাম; দুই theme-এই লেখা পড়ার মতো রাখতে (4.5:1) রং বদলানো;
    logo আবার সাধারণ PNG হিসেবে save করা
  - প্রতিটা brand-এর domain panel-এর server serve করে, নিজের certificate-সহ, আর sign-in page-এ নিজের brand দেখায়;
    notification-এর link-এ এটাই থাকে
  - Source code-এর link থাকে, AGPL যেমন চায়
  - VM-এ চালিয়ে দেখা: panel-এর আর একজন reseller-এর domain নিজেদের certificate আর brand নিয়ে একজন customer-এর
    website-এর পাশে serve হওয়া, reseller-এর domain-এ sign in, reseller-এর branding তুলে নিয়ে আবার দেওয়া, আর installer-এর
    Caddyfile আগে থেকেই serve করে এমন domain

বাকি আছে:

- বাছাই করা permission-সহ sub-user (4e-5)

### 4f. Security center

- প্রতি site-এ একটা WAF (OWASP Core Rule Set-সহ Coraza), প্রথমে শুধু detect করবে
- প্রতি site-এ আর panel-এর sign in-এর জন্য rate limiting; CrowdSec পড়ে না এমন service-এর জন্য blocking

### 4g. Billing integration

- WHMCS, Blesta আর Paymenter-এর জন্য provisioning module, panel-এ single sign-on-সহ
- এরপর built-in billing (Stripe, bKash, SSLCommerz), তখনো চাওয়া হলে

### আগের phase থেকে বাকি থাকা ছোট জিনিস

যেখানে মানায় সেখানে এগুলো সাথে নেওয়া হবে:

- একটা database browser, আর database import ও export
- আলাদা আলাদা file restore করা, আর একটা backup download করা
- Cloudflare বা built-in DNS দিয়ে wildcard certificate (DNS-01)
- Cloudflare API আর বাইরের mail delivery আসলভাবে চেষ্টা করে দেখা
