You can bring a whole cPanel account over to one of your servers from its full backup (the
`cpmove` file): its websites with their files, its MySQL databases with the same names, users
and passwords, and its cron jobs. You choose what to import, the panel sets it up, and a report
tells you what came over and what did not. Nothing changes for visitors until you point the
domains at the new server.

## Before you start

- You are an **administrator**. Customers do not see this page; you can import an account
  for a customer.
- **The server is connected**: it is [added to the panel](/start/add-server/) and shows
  **Online** on the **Servers** page. The websites will run on this server.
- **The server has enough free disk space** for the backup file plus everything in it once
  unpacked: the account's files and its databases. cPanel shows both sizes on its home page.
  Check **Disk** on the server's page; the panel does not check this for you.
- **You can copy files to the server** over SSH (with `scp` or an SFTP program such as
  FileZilla), as `root` or a user with `sudo`.
- To import for a customer, their [package](/guides/admin/customers/) must allow the server and
  have room for the websites, databases and cron jobs you bring over.

## Make the backup in cPanel

You need a **full account backup**, not a home folder or database backup on its own. Any of
these gives one:

- **In cPanel**: open **Backup** and click **Download a Full Account Backup**. cPanel makes the
  file in the background and tells you when it is ready.
- **From the old host**: ask for the account's `cpmove` file.
- **In WHM**, if you have it: **Transfer or Restore a cPanel Account**, or on the old server's
  command line:

  ```bash
  sudo /scripts/pkgacct <cpanel user>
  ```

The file has a name like `cpmove-USER.tar.gz` (or `backup-…_USER.tar.gz` from cPanel's
**Backup** page). The panel accepts `.tar.gz`, `.tgz` and `.tar` files.

## Put the backup on the server

The server's agent only reads backups in one folder: `/srv/ekpanel/imports/` (the agent makes
it, readable only by root). Copy the file there from your computer:

```bash
scp cpmove-USER.tar.gz root@203.0.113.20:/srv/ekpanel/imports/
```

Replace `203.0.113.20` with the server's address and `cpmove-USER.tar.gz` with the file's
name. The **Import from cPanel** page shows the `scp` line for the server you choose, with a
copy button.

<Aside type="caution">
The backup holds every file of the account and the password hashes of its databases. Keep it
only as long as you need it, and [delete it after the import](#after-the-import).
</Aside>

## Read the backup

<Steps>

1. In the sidebar, under **Administration**, click **Import**. You can also press `Ctrl+K` and
   type "Import".

2. In **Server**, choose the server you copied the backup to.

3. In **Backup file name**, enter the file's name only, without a folder:
   `cpmove-USER.tar.gz`, not `/srv/ekpanel/imports/cpmove-USER.tar.gz`.

4. Click **Read backup**. "Reading the backup. A large one can take a few minutes."

</Steps>

The panel then shows **2. Choose what to import from _user_**, with the cPanel user name and
the size of its home folder.

## Choose what to import

<Steps>

1. Under **Websites**, tick the websites to import. Each one is marked **Main domain**,
   **Addon domain** or **Subdomain**, with its document root (such as `~/public_html`).
   Parked domains are not websites of their own: they show as "Also: …" under the main domain
   and become its extra domains.

2. Next to each website, check its **PHP** version. It starts at the version the website had in
   cPanel ("was 8.0" shows when that version is not offered here). ekPanel offers 8.5, 8.4,
   8.3, 8.2, 8.1 and 7.4; any other version becomes 8.4. A customer's package may allow only
   some versions; then the first one it allows is used.

3. Under **Databases**, tick the MySQL databases to import. Each one shows its size and its
   user. "gets a new password" means the password could not be carried over (see
   [Databases](#databases)).

4. If the account has cron jobs, the box with their number (for example **3 cron jobs**) imports
   all of them. They go to the main website, so it can only be ticked when the main website is
   ticked too.

5. In **For**, choose who owns what you import: **Administrators (no package)** or a customer.

6. Read the **Not imported yet** box, then click **Import**.

</Steps>

Websites whose domain is already used by a website or app on the panel are marked
**Already here**, and so are databases whose name (or user) the server already has. They cannot
be ticked. The line next to the **Import** button counts what you chose, such as
"3 websites, 2 databases".

Clicking **Import** makes the websites and databases in the panel at once, then a task fills
them: "The websites and databases are being set up, then the files and data are copied in. You
can leave this page; the import goes on." While it runs, the tasks box at the bottom of every
page shows it as "Import cPanel account _user_".

## What the import does

In a test VM, a small account (a PHP 8.2 website with a MySQL database, a parked domain, a
symbolic link and a cron job) was read and imported in about 5 seconds, or 51 seconds when the
server had to install PHP 8.2 first. A large account takes as long as its files take to unpack.

### Websites and files

- Each website you chose becomes a **PHP website** with a Linux account of its own. The
  account gets a new name made from the domain (as for any new website), not the cPanel user
  name.
- The files in a website's document root go to its `public_html`. An addon domain whose folder
  is inside `public_html` gets only its own folder; the main website gets the rest.
- Other files and folders in the cPanel home folder, outside every document root (scripts,
  private folders), go to the **main website's** home folder, next to its `public_html`. If you
  did not import the main website, they are left out.
- Left out: cPanel's own folders (`mail`, `etc`, `.cpanel`, `tmp`, `logs`, `access-logs`,
  `ssl`, `.trash`, `public_ftp`, `.htpasswds`, `.softaculous` and similar), other dotfiles and
  dotfolders in the home folder (except `.well-known`), symbolic links that point outside the
  website, and special files such as pipes. The report counts them.

### Databases

- Each database you chose becomes a MariaDB database on the server, with the **same name**,
  the **same user** and the **same password**: the password hash is carried over. Your
  `wp-config.php` and other settings keep working without a change.
- In ekPanel, each database has one user of its own. In cPanel, one user can serve several
  databases: then the first database keeps the user, and each other one gets a new user named
  like the database, with a new password. A database that had no user also gets one, with a new
  password.
- The report lists the databases with new passwords. For each one, open it under **Databases**,
  click **Create a new password**, and put the database's user and new password into the
  website's settings. See [Databases](/guides/data/databases/#reset-a-password).

### Paths in files

Old code and settings often name the cPanel home folder, such as
`/home/olduser/public_html/wp-content`. The import changes `/home/<cPanel user>/…` to the new
place in small text files:

- a path into a website's document root becomes that website's `public_html`;
- any other path becomes the main website's home folder.

Only files up to 1 MB are changed, and only code and configuration: `.php`, `.inc`, `.ini`,
`.env`, `.htaccess`, `.user.ini`, `.json`, `.yml`, `.yaml`, `.xml`, `.conf`, `.cfg`, `.sh`,
`.pl`, `.py`, `.cgi` and `.txt`. The report counts the files it changed and lists them.

Paths stored **inside databases** (for example in WordPress's `wp_options` table, or a
cache plugin's settings) are not changed. If a website still names the old folder, change
them with the website's own tools, such as `wp search-replace` for WordPress.

### Cron jobs

- The cron jobs are added to the main website and run as its account.
- `/home/<cPanel user>/` in a command changes to the main website's home folder.
- The PHP binaries cPanel uses (`/usr/local/bin/php`, `/opt/cpanel/ea-php82/root/usr/bin/php`,
  `ea-php82`, `php`) change to the main website's PHP version, such as `php8.2`.
- Settings lines such as `MAILTO=…` are not imported; the report lists them. ekPanel keeps
  each job's output on its page instead. See [Cron jobs](/guides/websites/cron/).

### The report

When the task ends, the page shows **Import finished** with the websites, the databases, the
number and size of the files, and the number of cron jobs, then:

- "The old home folder's path was changed in _n_ files", with the list;
- the databases with new passwords;
- **Not imported**: everything that was left out, such as email accounts, DNS zones,
  certificates, cPanel's folders and links that point outside a website.

## After the import

<Steps>

1. **Check each website before you switch DNS.** Point the domain at the new server on your
   computer only, by adding a line to its `hosts` file (`/etc/hosts` on Linux and macOS,
   `C:\Windows\System32\drivers\etc\hosts` on Windows):

   ```text
   203.0.113.20  example.com www.example.com
   ```

   Open the website in your browser and try a few pages, a login and a form. Your browser warns
   about the certificate: the server gets a real one only once DNS points to it. Remove the
   line when you are done.

2. **Recreate what was not imported**: email accounts under [Email](/guides/dns/email/), and the
   DNS zones under [DNS](/guides/dns/name-servers/) (or keep them at your current DNS host).

3. **Point the domains at the server.** Change each domain's `A` record (and `AAAA`, if you have
   one), and those of the extra domains, to the server's address. Certificates are issued by
   themselves once the domains point there.

4. **Delete the backup** from the server:

   ```bash
   sudo rm /srv/ekpanel/imports/cpmove-USER.tar.gz
   ```

</Steps>

<Aside type="caution" title=".htaccess files do nothing here">
ekPanel's web server (Caddy) does not read `.htaccess` files. The usual "send every request to
`index.php`" rule of WordPress, Laravel and similar is built in, so their pretty links keep
working. Other rules in `.htaccess` (redirects, blocked folders, password protection,
`php_value` lines) are ignored: recreate them under [Redirects](/guides/websites/redirects/) and
the website's [PHP settings](/guides/websites/php/#php-settings-per-site).
</Aside>

<Aside type="note">
A website's home folder (`/home/<account>`) is read-only for the website's own account, because
SFTP locks the account into it. Scripts that wrote files straight into `/home/<cPanel user>/`
must write into a folder inside it instead, such as `tmp` or a folder of their own. See
[Files](/guides/websites/files/).
</Aside>

## With the API

An administrator's [API token](/guides/security/api-tokens/) with the `sites` scope can import.
Customers' tokens cannot.

| Endpoint | What it does |
| --- | --- |
| `POST /api/v1/imports/inspect` | Read a backup. Body: `{"server_id": "…", "file": "cpmove-USER.tar.gz"}`. Answers with what is inside, and with `taken_domains`, `taken_databases` and `php_versions`. |
| `POST /api/v1/imports` | Import. Body: `{"server_id", "file", "owner_id", "sites": ["example.com"], "php": {"example.com": "8.2"}, "databases": ["olduser_wp"], "cron": true}`. Answers `202` with a [task](/reference/api/#tasks-following-slow-work); its `result` holds the report. |

Leave `owner_id` empty for administrators. With [ekctl](/reference/cli/#any-endpoint-ekctl-api):

```bash
ekctl api POST imports/inspect --data '{"server_id":"<server id>","file":"cpmove-USER.tar.gz"}'
ekctl api POST imports --data '{"server_id":"<server id>","file":"cpmove-USER.tar.gz","owner_id":"","sites":["example.com"],"databases":["olduser_wp"],"cron":true}'
```

## Limits and what is not there yet

These parts of a cPanel account are **not imported yet**. They are planned; see the
[roadmap](/project/roadmap/).

- **Email accounts and mail.** Recreate the mailboxes under [Email](/guides/dns/email/) and move
  the mail with your mail program, or with a tool such as `imapsync`.
- **DNS zones.** Add the records under [DNS](/guides/dns/name-servers/), or keep the zone at
  your current DNS host and change only the `A` and `AAAA` records.
- **SSL certificates.** New ones are issued once the domains point to the server.

Also:

- Only MySQL databases are imported, as MariaDB databases. PostgreSQL databases in the backup
  are left out.
- Every website becomes a PHP website. Node.js, Python and Ruby applications from cPanel are
  copied as files but do not run; set them up as [apps](/guides/apps/docker-apps/).
- FTP accounts and cPanel's own settings are not imported. Redirects and password-protected
  folders made in cPanel live in `.htaccess` files, which ekPanel does not read (see
  [After the import](#after-the-import)).
- One backup is imported to one server.
- Tried in a test VM with a small backup built like cPanel's, not yet with backups from many
  real cPanel servers.

## Troubleshooting

| Message | What to do |
| --- | --- |
| "Enter the name of a .tar.gz backup in /srv/ekpanel/imports on the server, without a folder." | Enter only the file name, ending in `.tar.gz`, `.tgz` or `.tar`. |
| "No backup with that name is in /srv/ekpanel/imports on this server. Check the file name and the server." | The file is on another server or has another name. Check with `ls -l /srv/ekpanel/imports/` on the server you chose. |
| "This file is not a cPanel full backup, or it is damaged. Make a full account backup in cPanel and copy it again." | The copy is incomplete (compare its size with the original) or the file is another kind of backup, such as a home-folder-only backup. Make a full account backup and copy it again. |
| "The server's agent is not connected." | The server is offline. See [When a server goes offline](/guides/admin/servers/#when-a-server-goes-offline). |
| "Already used by another website or app here: …" | Another website or app on the panel uses that domain. Untick the website, or delete the other one first. |
| "The server already has a database or user named …" | Untick the database, delete or rename that database or user on the server, or import to another server. |
| "Your package allows no more websites." (or databases, cron jobs) | Raise the customer's package limits, or import less. |
| "This package cannot use that server." | Add the server to the customer's package, or choose another server. |
| "Choose at least one website or database." | Tick at least one. |

**The import failed.** The page shows **The import failed** with the reason. "Websites and
databases the panel made for it are still listed. Delete them before you try again." Then
read the backup again and import.

**A website shows a database error.** Check the report for databases with new passwords, and
put the new password into the website's settings. If a database was not imported, import it
again on its own: read the backup again and tick only that database.

**A website shows the wrong files or old paths.** Look for paths to `/home/<cPanel user>/` that
the import did not change: in files larger than 1 MB, in files of other types, or in the
database.
