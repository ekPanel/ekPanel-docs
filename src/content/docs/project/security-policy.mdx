ekPanel controls servers with root privileges, so security reports come first. This page says
how to report a vulnerability privately and what happens after you do. It summarises
[`SECURITY.md`](https://github.com/ekPanel/ekpanel/blob/HEAD/SECURITY.md) in the main repository
and the [organisation's security policy](https://github.com/ekPanel/.github/blob/HEAD/SECURITY.md).

<Aside type="danger" title="Never report a vulnerability in public">
Do not open a public issue, pull request or discussion about a security problem, and do not
post it in a chat. Report it privately, as below.
</Aside>

## How to report

Use one of these:

- **GitHub's private vulnerability reporting** on the affected repository: the **Security** tab,
  then **Report a vulnerability**. Only the project's maintainers see the report.
- **Email** to **ekpanelbd@gmail.com**, with "Security" in the subject.

## What to include

<Steps>

1. **What an attacker can do**, and what they need first: an account (administrator or
   customer?), network access, a website on the same server…

2. **How to reproduce it**: steps, or a proof of concept.

3. **The versions**: the output of `ekpanel version` and `ekpanel-agent version`, or the commit
   you tested.

</Steps>

Please remove real passwords, keys and personal data from what you send.

## What happens next

- We aim to **acknowledge** your report **within 3 days**.
- We aim to **fix critical problems within 14 days**.
- We **credit reporters** in the release notes, unless you prefer not to be named.

## Supported versions

ekPanel is in early development. The first release, v0.1.0, is out, but there is **no stable
release yet**, so there are no supported versions in the usual sense. Fixes go into the `dev`
branch and come out in the next release, so keep your panel on the newest one. Once stable
releases exist, this page will say which ones get security fixes.

## What counts

SECURITY.md lists the design principles ekPanel promises. A good rule: anything that breaks one
of these promises is a vulnerability we want to hear about. Some examples:

- a customer seeing or changing something that is not theirs
- a website's files, PHP, cron job, FTP or SFTP login reaching outside its own folder or account
- the agent doing something that is not one of its typed operations, or accepting unchecked
  input from the panel
- getting into the panel without the password (and two-factor code, or one of the account's
  recovery codes or passkeys), or around the setup token
- cross-site request forgery or script injection in the web UI
- secrets showing up where they should not: in logs, API answers, the process list, or files
  other accounts can read
- a firewall, country blocking or CrowdSec rule that ekPanel says it never makes (for example,
  one that blocks the administrator's own address)

If you are unsure, report it anyway.

## How ekPanel is built for security

A short version of SECURITY.md's design principles:

- The agent accepts only typed, validated operations from a fixed list. The only way to run an
  arbitrary command is the web terminal, an interactive shell for a person, which asks for the
  password again and is recorded in the audit log.
- Panel and agents talk over mutual TLS with a private CA that agents pin at enrolment.
  Certificates last 90 days and renew automatically.
- Passwords are hashed with argon2id; session and enrolment tokens are stored only as hashes.
  Database, FTP and mailbox passwords are stored only as the services' own hashes.
- Every website runs as its own Linux account with its own PHP-FPM pool and `open_basedir`.
- State-changing requests are protected against cross-site requests; session cookies are
  `HttpOnly`, `SameSite=Lax` and `__Host-` prefixed; a strict Content-Security-Policy allows no
  inline scripts.
- Every change is written to an append-only audit log that the database refuses to modify.

See [Security model](/concepts/security-model/) for how these fit together.
